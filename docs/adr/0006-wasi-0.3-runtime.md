# ADR 0006: Adopt WASI 0.3 as the WebAssembly runtime baseline

- **Status:** Accepted
- **Date:** 2026-07-15
- **Compatibility scope:** unreleased v0.x

## Context

Runtrue executes signed WebAssembly Components with an embedded Wasmtime
executor. The initial implementation pinned Wasmtime 36.0.12 and only linked
the Runtrue-owned `runtrue:action/run@1.0.0` contract. That runtime predates the
final WASI 0.3 release.

WASI 0.3.0 was released on 2026-06-11. It adds native Component Model
asynchrony through `async func`, `future<T>`, and `stream<T>`, and is the only
published 0.3.x version at the time of this decision. Wasmtime 46 is the first
release line that ships final WASI 0.3.0 support by default. Wasmtime 46.0.1
requires Rust 1.94.

Runtrue has not published a release, so carrying the Wasmtime 36 runtime or a
parallel compatibility mode would add cost without protecting users. The
runtime still needs an explicit authority boundary: linking WASI must not
inherit the runner process's environment, files, standard streams, or network.

The standard WASI substrate and the Runtrue action interface are separate
contracts. A component may import WASI 0.3 interfaces while exporting the
current Runtrue action entry point. A later asynchronous Runtrue action world
will require its own ADR because changing the exported `run` function changes
the action ABI, Capsule identity, cancellation behavior, and host-adapter
contract.

## Decision

### Runtime and toolchain

Runtrue replaces the old baseline with:

- WASI 0.3.0;
- Wasmtime and `wasmtime-wasi` 46.0.1;
- Rust and workspace MSRV 1.94; and
- Wasmtime's Component Model async and byte features enabled.

Enabling Wasmtime's async machinery is an embedding requirement for the P3
implementation, not a claim that every asynchronous P3 interface is admitted.

There is no Wasmtime 36 or WASI 0.2 compatibility path. The current runtime
supports the latest published member of the WASI 0.3.x release train. A later
0.3.x update is a deliberate pinned dependency change, not an open version
range at runtime.

The action contract remains `runtrue:action/run@1.0.0`. This is not a legacy
WASI mode: the action ABI is Runtrue-owned and independent from the WASI import
version. The executor admits components that export the exact action entry
point and whose imports are members of the exact closed allowlist in the signed
runtime profile. Merely adding an interface to the Wasmtime linker does not make
it admissible.

The initial profile admits the synchronous action-v1 host contract and the
specific non-streaming P3 imports exercised by the fixture and selected
nondeterminism profile. It rejects futures, streams, guest task spawning,
asynchronous host calls, and any unlisted P3 interface before instantiation.
Each allowlist change creates a new runtime compatibility identity.

### Authority boundary

Each invocation receives a fresh `WasiCtx` and resource table. Its baseline is:

- no environment variables or arguments;
- no initial working directory or preopened directories;
- closed stdin and sink stdout/stderr;
- TCP and UDP disabled, all addresses denied, and DNS lookup disabled; and
- no inherited host process handles.

Guest-visible clocks and random sources are denied unless the Capsule selects
an exact versioned nondeterminism profile. The initial profiles are:

- deterministic virtual time and pseudorandom input derived from sealed,
  content-addressed inputs for tests and replay; and
- live time and cryptographic randomness from the Provider for Programs that
  require real nondeterminism.

The deterministic profile is test/replay-only and never claims cryptographic
randomness. A production Capsule that requires security-sensitive entropy must
select the live profile and accepts its replay limitation.

Evidence records the selected profile and bounded use, never a secret entropy
value. Use of a live source prevents a Hermetic or Exact Replay Bundle unless a
future policy-safe recorded-interaction contract captures everything required
for replay. Bisim fixtures that compare Program output use deterministic
sources; Provider differences are never normalized out of Program results.

Filesystem, network, secret, OIDC, and output authority continues to use
Runtrue's explicit Capsule-bound handles and bounded adapters. Runner
environment, process execution, unsealed clock or random imports, and fallback
to another executor remain forbidden.

Any future decision to preopen a directory, expose standard streams, add
arguments or environment, or permit a WASI socket must bind that authority to
the Capsule and policy. It must not use an `inherit_*` convenience API.

### Identity, admission, and caches

The exact WASI version is included in the signed component compatibility map
and the authenticated AOT cache key alongside:

- action world and WIT digest;
- exact Wasmtime version;
- target triple and CPU feature floor;
- compiler settings and engine compatibility digest; and
- security mitigation profile.

A mismatch fails before execution. Upgrading Wasmtime, WASI, the WIT contract,
or the authority profile creates a different cache identity, so an older AOT
artifact cannot be reused accidentally.

The executor never retries a failed component under a different WASI version,
executor, or isolation mode.

### Verification and E2E readiness

The repository includes a deterministic component fixture that imports
`wasi:cli/environment@0.3.0`. The local test path:

1. builds the Component Model binary from pinned WAT tooling;
2. creates and verifies its signed component manifest;
3. admits and compiles it under the exact runtime tuple;
4. links the WASI 0.3 host with an empty ambient environment;
5. executes the Runtrue action entry point; and
6. verifies successful terminal output; and
7. verifies that components importing futures, streams, task spawning,
   asynchronous host calls, or any unlisted interface fail admission.

The fixture also produces a digest-pinned workflow bundle for a future managed
Runtrue deployment. Managed E2E must use the same component digest and verify
both a cold compile and authenticated AOT cache hit. Until a second conforming
Provider exists, the local signed-executor test is a development and merge gate,
not a portable release-conformance claim or a remote transport test. The WASI
0.3 profile must not be advertised as release-conformant until it passes the
ADR 0014 Bisim, Provider, and runtime-specific gates.

Before an asynchronous import or Runtrue action ABI enters an admitted profile,
Runtrue must gate it with positive and adversarial coverage for futures,
streams, backpressure, timeout and cancellation during host awaits, task-tree
cleanup, late host calls after cancellation, and resource exhaustion. The
allowlist remains closed until those tests pass locally and through ADR 0014
conformance. Bisim will compare local and managed execution once the managed
runtime exists.

## Consequences

- Runtrue can execute components with final WASI 0.3 imports now.
- The runtime upgrade increases the workspace MSRV from Rust 1.88 to 1.94.
- Ambient host access stays closed; guest time and randomness require an exact
  Capsule-bound profile, and linker availability never bypasses the admitted P3
  import allowlist.
- Cache and signed-manifest compatibility explicitly identify WASI 0.3.0.
- A WAT fixture gives deterministic E2E coverage without depending on a guest
  language shipping a low-tier `wasm32-wasip3` standard library.
- Native asynchronous action exports and stream/future adapters remain a
  separate, test-gated action ABI change.

## Review triggers

- A WASI 0.3.x release supersedes 0.3.0.
- Wasmtime changes the stability or security support of its P3 embedding API.
- A guest toolchain provides a reproducible WASI 0.3 component target suitable
  for the primary SDK example.
- Runtrue adds an asynchronous action entry point or exposes a new WASI
  authority.
- Managed Bisim or E2E evidence differs from the local executor result.
